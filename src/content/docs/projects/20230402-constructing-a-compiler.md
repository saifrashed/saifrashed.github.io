If you want to completely change the way you look at program code, then I recommend constructing a compiler. These programs are used to translate high-level human readable programming languages into machine-executable code, typically instructions in assembly. The [multi-pass](https://en.wikipedia.org/wiki/Multi-pass_compiler) compiler in this article compiles a C-like language into assembly, however, it is just one type of many.

## From code to tokens
Compiling source code starts by translating the character stream into meaningful units called tokens. Essentially, we define tokenization rules in a lexical analyzer. These rules determine what keywords and symbols are valid in the source programming language. Some language elements can be captured with regular expressions, for example one and multi-line comments. The code snippet below shows a few of these rules defined for the [Flex](https://github.com/westes/flex) lexical analyzer. 

```c

"/*"((("*"[^/])?)|[^*])*"*/" { /* A COMMENT, DO NOTHING WITH IT */ }
"//".*                       { /* A COMMENT, DO NOTHING WITH IT */ }

"if"					               { FILTER( IF); }
"else"				               { FILTER( ELSE); }
"while"				              { FILTER( WHILE); }
"do"				                 { FILTER( DO); }
"for" 				               { FILTER( FOR); }
```

Everytime a sequence of characters in the code stream matches a rule, a token is produced, eventually we are left with a sequence of tokens that represent our code. In our example above we deal with comments, and the language we are compiling from, like many other languages, do not handle any commented text, so we do not produce any tokens for it, but we do for any other construct such as function definitions, producing the example below.  

```
# Function definition from the source code
int main() {}


# Token output produced by the lexical analyzer
INTTYPE
ID(main)
ROUNDBRACKET_L
ROUNDBRACKET_R
CURLYBRACKET_L
CURLYBRACKET_R

```

Finally, we debugged the lexer and were sufficiently confident in the lexers ability to produce a correct sequence of tokens, the lexer was integrated into the compiler, forming the foundation for our compiler. 


## Giving structure to tokens
At this point, the token sequence generated by our lexer is not necessarily correct, we haven't defined what "correct" means yet. By creating a grammar, we define the syntactic structure of the language. We begin by defining the constants and expressions as specified in the language. We define statements, parameters and arguments by creating three types of grammars for each: singular, one or many, and optional many grammars, but could also be handy for function definitions that do not have any parameters.

```c
block:  CURLYBRACKET_L stmts_opt CURLYBRACKET_R
      {
        $$ = $2;
      }
      | stmt
      {
        $$ = ASTstmts($1, NULL);
      };
```

 Some grammars, like those of function definitions and variable declarations, do not fit into a single rule. They can grow unmanageable and increase the chance of ambiguities (shift/reduce conflicts). To solve this, we split the grammar rules. Finally, if parsed correctly with a tool like Yacc, an [Abstract Syntax Tree (AST)]() is produced, to be used as an intermediate representation during succeeding compilation steps.


## Determining Semantics
The semantic analysis uses the Abstract Syntax Tree (AST) and a Symbol Table to perform tasks like type checking, scope resolution, and variable declaration checks. We traverse the AST with a helper method, enabling inspection and manipulation of the intermediate representation. 

During the traversals we need some way to keep track of identifiers. For this, a symbol table is devised, and implemented with a symbol table node, used to construct a linked list, attaching it to the global program and function definition nodes. The node consists of a initial head (child) symbol table entry node and an outer symbol table entry (child) node that references the parent symbol table node. We create helpers to create a new symbol table entry, and append it to the end of the symbol table head node, and link the entry to the declaration being visited. If an entry was already defined, it raises an error message. For the software engineers among us, this error message might look familiar to anyone who has spent late nights debugging: `SyntaxError: Identifier 'x' has already been declared`. These errors force us to learn the difference between assignment and initialization.

To prepare for code generation, we focused on normalizing program structures:

- Induction Removal: Standardizing loop shapes.
- Variable Initialization: Separating assignments and relocating global setups to a generated _init function.
- Name Binding: Linking AST nodes (like function calls) to their definitions.
- Type Checking: The final phase using bottom-up inference to detect mismatches and validate operations.


## Generating machine instructions 
To prepare for code generation, we first implemented several AST transformations designed to simplify the backend logic. This included standardizing control flow by converting `for` loops into equivalent `while` loops and injecting ternary conditions to handle negative step values. 

```c
// Source
for (i = 0; i < 10; i = i + 1) { ... }

// Transformed (Conceptually)
i = 0;
while (i < 10) {
   ...
   i = i + 1;
}
```

We also rewrite boolean operations into ternary structures to natively preserve short-circuit evaluation. With the AST normalized, I reverse-engineered the reference compiler’s output to understand these structures and implemented a tracking system that assigns an `assembly_index` to every Symbol Table Entry (STE). This allows variable nodes to resolve their correct table location during the final traversal, where `fprintf` instructions generate the bytecode. I verified the result by comparing my output against the reference compiler and running custom test suites covering edge cases like casting, nested loops, and complex branching.


## Final thoughts
Compilers are incredibly intriguing systems, powering the world with enormous leverage. Optimizations at this level can lead to massive gains when projected forward; these gains span multiple metrics, including speed, energy efficiency, and reliability. A single article can not fully do justice to underlying concepts like Context Free Grammars (CFGs), Non-deterministic Finite Automatons (NFAs) and endless set of optimizations.

Ultimately, building a compiler plants a seed of curiosity. It changes your perspective from simply writing code to understanding how that code interacts with the machine, revealing where software engineering truly intersects with hardware constraints.
