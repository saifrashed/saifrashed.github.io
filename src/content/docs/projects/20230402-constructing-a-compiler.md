## 1. Introduction
If you want to completely change the way you look at program code, then I recommend constructing a compiler. These programs are used to translate high-level human readable programming languages into machine-executable code, typically instructions in assembly. The compiler comes in many flavours, but for this project we implement a [multi-pass](https://en.wikipedia.org/wiki/Multi-pass_compiler) compiler, for a C-like language designed by the University of Amsterdam.

## 2. Lexicographic analysis
Compiling source code starts by translating the character stream into meaningful units called tokens. Essentially, we define tokenization rules in a lexical analyzer. These rules determine what keywords and symbols are valid in our programming language. For some language elements we use regular expressions, for example for one and multi-line comments. The code snippet below shows a few of these rules defined for the [Flex](https://github.com/westes/flex) lexical analyzer. 

```c

"/*"((("*"[^/])?)|[^*])*"*/" { /* A COMMENT, DO NOTHING WITH IT */ }
"//".*                       { /* A COMMENT, DO NOTHING WITH IT */ }

"if"					               { FILTER( IF); }
"else"				               { FILTER( ELSE); }
"while"				               { FILTER( WHILE); }
"do"				                 { FILTER( DO); }
"for" 				               { FILTER( FOR); }
```

Under the hood regular expressions make use of *Non-Deterministic Finite Automaton (NFA)* to determine if a string is in the language. This abstract machine is comprised of states and transitions, the machine accepts or rejects a string. The deciding factor for accepting a string is the final state of the NFA. For example, the expression ```"//".*```  accepts strings like ``` // This is a comment ``` because the characters transition it to an accepting state, or as shown in the image below, state ```Q2```.

<figure style="margin: 2rem 0; text-align: center;">
  <img src="/assets/constructing-a-compiler/automaton.png" alt="Compiler architecture diagram" style="max-width: 100%; height: auto; border-radius: 8px;" />
  <figcaption style="margin-top: 0.5rem; font-size: 0.9rem; color: #666; font-style: italic;"> The NFA for "//".* also happens to be a Deterministic Finite Automaton (DFA)  </figcaption>
</figure>

Essentially, any time the accepting state is reached, a token is produced, eventually the complete input source code is represented as a sequence of tokens. In our example above we deal with comments, and the language we are compiling from, like many other languages, do not handle any commented text, so we do not produce any tokens for it, but we do for any other construct such as function definitions, producing the example below.  

```
# Function definition from the source code
int main() {}


# Token output produced by the lexical analyzer
INTTYPE
ID(main)
ROUNDBRACKET_L
ROUNDBRACKET_R
CURLYBRACKET_L
CURLYBRACKET_R

```

Finally, we debugged the lexer and were sufficiently confident in the lexers ability to produce a correct sequence of tokens, the lexer was integrated into the compiler, forming the foundation for our compiler. 


## 3. Syntactic analysis
At this point, the token sequence generated by our lexer is not necessarily correct, that is to say that we did not define 'correct' yet. By creating a grammar, or to be specific, a [Context-Free Grammar (CFG)]() we are able to define the syntactic  structure of the language. If parsed correctly, with a tool like Yacc, it produces an [Abstract Syntaxt Tree (AST)](), used as an intermediate representation during succeeding compilation steps.

### Constants and expressions
Before starting with the higher-level grammars, we begin by defining the constants and expressions as specified in the language. We define statements, parameters and arguments by creating three types of grammars for each: singular, one or many, and optional many grammars, but could also be handy for function definitions that do not have any parameters. Some grammars, like those of function definitions and variable declarations, did not fit in one rule, it grew too large and unmanageable, and we encountered ambiguities that resulted in so called shift/reduce conflicts. 

To resolve this issue, we split the grammars into multiple parts. This approach brought order to chaos, improving the reusability of grammar. While defining the grammar for variable declarations, we encountered persistent shift/reduce conflicts. These ambiguities arose because the parser could not deterministically decide whether to extend the current declaration list or terminate it. To achieve a deterministic grammar, we refactored the production to be left-recursive. This eliminated the ambiguity by forcing the parser to reduce as it consumed tokens from left to right. However, left-recursion in bottom-up parsing naturally produces a left-leaning tree, which results in the elements being collected in reverse chronological order.


 For example, we encountered ambiguities with ```vardecls```, resolved by making the ```vardecls``` [left-recursive](https://www.ibm.com/docs/en/zvm/7.3.0?topic=topics-right-recursion-versus-left-recursion), but this resulted in the ```vardecls``` being reversed. To address this, we implemented a quick and robust solution that solved the issue:

```c
vardecls: vardecls vardecl  // example: int a = 5; int b = 4; int c;
      {
        node_st *current = $1; // take head of vardecls

        while(VARDECL_NEXT(current) != NULL) { // traverse it till the end
          current = VARDECL_NEXT(current);
        }

        VARDECL_NEXT(current) = $2; // in the end we place the given vardecl

        $$ = $1;
      }
      | vardecl
      {
        $$ = $1;
      };
```

Finally, after completing all the individual parts, we moved on to the global definition and declaration. This part was relatively straightforward, and with the grammar complete we were able to generate an AST, and proceed to the next phase.


## 4. Semantic analysis

The semantic analysis uses the Abstract Syntax Tree (AST) and a Symbol Table to perform tasks like type checking, scope resolution, and variable declaration checks. We traverse the AST with a helper method, enabling inspection and manipulation of the intermediate representation. 

### The Symbol Table
During the traversals we need some way to keep track of identifiers. For this, a symbol table is devised, and implemented with a symbol table node, used to construct a linked list, attaching it to the global program and function definition nodes. The node consists of a initial head (child) symbol table entry node and an outer symbol table entry (child) node that references the parent symbol table node. We end up with a structure like the one shown below.

We create helpers to create a new symbol table entry, and append it to the end of the symbol table head node, and link the entry to the declaration being visited. If an entry was already defined, it raises an error message. For the software engineers among us, this probably has you reminiscing about earlier days, when the countless ```SyntaxError: Identifier 'x' has already been declared``` errors triggered you to learn difference between variable assignment and initialization. 

Furthermore, we populate the table by traversing the following nodes: program, fundef, globdecl, globdef, vardecl, param, and ids. During traversal the root program or function definition node are persisted so that succeeding node visits have access to scope and store the identifier correctly. ### Induction removal & initialization

This compiler loop optimization involves extracting the induction variable into a new variable declaration and correctly seperating initialization from assignment. We do this in order to canonicalise the loops in our program to an uniform shape, making analysis and code generation easier to do. It is recursively applied to the inner body, in order to make it work for nested loops. The scheme below visualizes this process:

We do an initialization right before the for loop statement, for nested loops, to ensure that the variable is assigned the start value during loop iterations.

### Variable initialization
We describe this optimization in two tasks. First, we move and initialize global variables in a new ```_init``` function, created at compile time. Second, for variable declarations in functions, we seperate assignment values from the initialization, and move the initialization to the beginning and assignment after it. However, determining the correct scope for a variable caused several issues. The symbol table lookup function searches the entire table without considering scope boundaries or declaration order. As a result, a variable reference may incorrectly resolve to a declaration that appears later in the code or within a nested varlet block. In such cases, the reference should instead resolve to a previously declared variable in the current scope, or fall back to a global variable if one exists. To address this, I modified the lookup process to first check for a valid prior declaration in the current scope. If none is found, the search continues in the outer scope. If the variable is still not found, an undefined reference error is raised.

### Name binding
We see this step not as an optimization, but an semantic analysis pass, where the symbol table entries are matched with the correct AST node, focusing on varlet, var, and funcall nodes. This is a satisfying moment because it makes the data structures ready for the type checking analysis. For var and varlet nodes, nothing much changed, we simply use the lookup function to search all symbol tables from inner to outer and skip any nodes that already have an entry due to preceding optimizations.

```
/**
 * @fn NBfuncall
 */
node_st *NBfuncall(node_st *node)
{
    // Get the data and current scope
    struct data_nb *data = DATA_NB_GET();
    node_st *scope = data->current_scope;

    // Look up the function call in the symbol table
    char *signature = NBgeneratesignature(node);

    node_st *entry = NBlookup(FUNDEF_SYMTBL(scope), signature);

    // If the function is found, mark it as a function call entry
    if (entry != NULL)
    {
        FUNCALL_NAME(node) = signature;
        FUNCALL_ENTRY(node) = entry;
    }
...
```

However, for funcall nodes, things become more interesting. We used the *STgeneratesignature* function during symbol table creation to encode the arity of the fundef node. Now, we need to create a version that generates a signature for function calls by counting the arguments. We use this signature to search the symbol table, and if it exists, we have a match on arity. If it does not exist, we can conclude that the function signature does not match any other function. 

### Type checker
The goal of this analysis is to detect type mismatches and provide meaningful error messages when statements, functions, or variable declarations have disallowed types. To achieve this, we follow a similar approach as with the grammars. We start with low-level nodes, such as constants and variables, and gradually progress to higher-level nodes such as unary/binary operations, function calls, and other expressions. Essentially, we infer the types bottom-up: a constant like 5 is of type int, true is of type bool, and a string literal is of type string. By propagating type information upward through the abstract syntax tree and checking constraints at each level, we can systematically detect type inconsistencies and provide precise, context-aware error messages.

**Constants:**: In this part of type checking, I simply pass the num, float, and bool nodes and assign the inferred variable to one of these types. For var and varlet nodes, I do the same, but now I access the symbol table entry node and read the type from there.

**Expressions:**: For the binops and monops, I use a switch case, which suffices for my goal. First, I check the type of operator, and then depending on the combination of types, I infer a certain type. If none of the cases are met, I return an error message. For funcalls, I iterate through all arguments and simultaneously test them with the parameters of their function definition. Eventually, I infer the function definition type by accessing it in the symbol table. The cast node does the same, but here I already insert an ternary node for booleans that are casted to either float or num.

**Statements:**: For return statements, I use my trick of storing the scope in travdata to access the function definition. Now, I can test the types and send error messages if necessary. In the assign node, I traverse both sides and compare the types. However, it should be noted that assign type checking also includes globaldef and vardecl type checking. I also perform an indices check. For the rest of the statements, I simply check if the types are correct in place. For example, in a while loop, I would check if the condition is boolean.

**Function definition:**: Here, I use a ```TChas_return``` function to check if a function has a return statement or not. If it does not have a return statement when it is required, I send an error message. In addition to this, I simply traverse the children.

## 5. Code generation

To implement code generation, I had to make some optimizations that would allow the code generator to produce code easily. Once they were completed, I used a file pointer in the travdata to write to a file. For each of the nodes I traversed, I would use fprintf to output the correct instructions. But before going into more detail, let me first go through the optimizations.

### Preparation
Before starting the actual code generation, several preparatory transformations are performed on the AST to simplify later stages and keep the backend implementation minimal and consistent.

**Parameter passing**: We traverse through all fundef and funcall nodes and uses *PPadd\_expr\_before\_arg* and *PPadd\_id\_before\_arg* to insert new arguments in the funcall. For parameters I use *PPadd\_before\_param* function to add new parameters. I did not encounter any problems when creating this traversal so therefore I can keep it short.

**Loop transformation**: For code generation, we want to keep it simple, and not overcomplicate. This also means that we restrict ourselves to generating one loop type. Thus, transforming the for loop into an equivalent while loop. We achieve this with the following process:

<figure style="margin: 2rem 0; text-align: center;">
  <img src="/assets/constructing-a-compiler/loop-transformation.png" style="max-width: 100%; height: auto; border-radius: 8px;" />

It is easy to miss crucial considerations, such as the negative step value in for loops. This changes the behavior, and is fixed with a ternary statement that encodes this logic:

```c
node_st *condition = ASTternary(
    ASTbinop(CCNcopy(step), ASTnum(0), BO_gt),
    
    ASTbinop(ASTvar(NULL, STRcpy(FOR_VAR(node))), CCNcopy(FOR_STOP(node)), BO_lt),
    
    ASTbinop(ASTvar(NULL, STRcpy(FOR_VAR(node))), CCNcopy(FOR_STOP(node)), BO_gt)
);
```

**Boolean transformation**: In this transformation we rewrite logical operators using the ternary (conditional) operator. Specifically, ```A && B``` becomes ```A ? B : false``` and ```A || B``` becomes ```A ? true : B```, which preserves [short-circuit evaluation](https://en.wikipedia.org/wiki/Short-circuit_evaluation) while simplifying code generation.

### Code generator
In this part, The first thing I did was to produce assembly code with the reference compiler. By using the -o flag, I managed to generate an output file, which was crucial for generating code since it allowed me to compare both sides. The second step was to actually understand how the CiviC VM worked, and I struggled a lot with understanding what a constant runtime pool actually means in relation to the CiviC VM.

After some time, I understood that the CiviC VM consists of multiple tables, including import, export, global, and constant tables, and that each maps to a type of node. For example, a global definition would always be added to the global table, and each constant node above 2 would always be added to the constant table.

After understanding these nuances, I started building out the code generator. To keep track of the indexes of each table, I keep track of globals:

```c
int global_index = 0;    // index for global table
int constant_index = 0;  // index for constant table
int importfun_index = 0; // index for import function table
int importvar_index = 0; // index for import variable table

char *instruction_string = ""; // to be shown in the end
```

As you can see, we also have a string that is built up. This string contains all the pseudo instructions for the tables. The next step is to actually increment these values in the globdef, vardecl, param, and globdecl nodes. Before incrementing, I need to store the index somewhere so that var/varlets can have access to the correct table entry.

To do this, I create a new ```STE``` attribute called ```assembly_index``` which will store this information for me. Because all var/varlets are linked with the ```STE``` nodes, I can access the correct table index, but only have to determine the correct instruction. This is simply a set of if statements that check the node type.

Everything afterwards was quite straightforward. Eventually, after testing and comparing the reference compiler bytecode with mine, I created my own tests. These captured some edge cases:

*   ```core.cvc```: Contains my civic core.cvc code (without the rest since I did not manage the extensions)
*   ```complex_if.cvc```: Contains a complex if statement where I test if-else statements
*   ```casting.cvc```: I further tested casting values to make sure the values are still the same
*   ```nested_loops.cvc```: I nest different types of loops in each other to make sure I did not do anything wrong in the loop transform

## 6. Final thoughts
I recognize that there were opportunities for improvement in my approach. For example, I dedicated a lot of unnecessary time to array initialization, which could have been better allocated towards implementing function overloading. Despite this setback, I believe that my decision to design for all extensions (and attempt them) from the start was the right choice. It allowed me to take a helicopter view and looking further down the process to determine what would be useful and what was redundant. Because of this, I was able to create useful functions like the lookup functions, that saved me a lot of time. Each component of my project builds upon one another, and not doing so would have been a risky move since there was a possibility that I was able to do one or more extensions if time allowed for it.
Overall, I am pleased with the end result.
